# Open decisions (phases 3–6)

None of these are decided. Each has a recommendation; the PRD and technical design are written
assuming the recommendation, and requirements that depend on a decision are marked `Blocked: D-n`
in the PRD. Platform choices fixed by `standards/platform.md` (ECS/Fargate, Aurora PostgreSQL Global
Database with write forwarding, EventBridge/SQS, Secrets Manager/SSM, CloudWatch, CloudFormation,
GitHub Actions) are **not** open decisions (`PLAT-09`) and are not listed here.

| ID | Decision | Needed before | Options considered | Recommendation | Why | Status |
|----|----------|---------------|--------------------|----------------|-----|--------|
| D-1 | Application framework and Java version | P3-1 | Spring Boot 3 / Java 21; Quarkus / Java 21; Micronaut / Java 21; Jakarta EE on embedded server | **Spring Boot 3.x (latest GA 3.x line) on Java 21 LTS** | Standards don't lock a framework. Boot has first-party support for everything phases 3–6 need: OAuth2 resource server, Actuator health groups/probes, graceful shutdown, structured logging, Micrometer/OTel, Flyway, Testcontainers. Spring Cloud AWS covers SSM/Secrets Manager/SQS. Most common Java skill set. | Open |
| D-2 | Decomposition | P3-3 | Modular monolith with enforced boundaries; split into services now | **Modular monolith** (one deployable, one schema, module boundaries enforced by ArchUnit) | Keeps behavior parity provable with one test suite. Notifications or customer can be extracted later along the module seams (`PLAT-04`: one schema per service then). | Open |
| D-3 | UI fate (JSP pages) | P5-5 | Keep JSP on Boot (WAR packaging); new SPA in this repo; **API-only**, UI later in its own repo | **API-only; retire JSP in P5-5.** Keep JSP working through phases 3–4 so the integration env stays usable. | JSP forces WAR packaging and server-side rendering of PII, and needs a separate browser auth flow. An API-only service makes OIDC and headers simpler. | Open |
| D-4 | Service tier | P5-6 (SLIs), phase 8 | `standard`, `tier-0` | **`standard`** | Nothing shows loan origination is customer-critical for this demo estate. Under `standard`, `RES-07`/`RES-08`/`PLAT-10` are still `must`. `ARCH-04` is `must` anyway because of `PLAT-10`. | Open |
| D-5 | Identity provider, callers and roles | P5-4 | Org OIDC IdP; Amazon Cognito; other | **Org-standard OIDC IdP.** Callers: internal channel apps (client-credentials) and staff users. Scopes: `loan.eligibility.check`, `loan.application.write`, `loan.application.read`, `loan.customer.read`. Roles map to scopes: `channel-app` → check + write + read; `underwriter` → read + customer.read; `admin` → all. **No direct applicant (end-customer) access in phases 3–6.** Locally: HMAC-signed test JWTs. | Applicant access would need per-customer ownership checks on `/v1/customers/{id}` and `/v1/applications/{id}`. That is new behavior the legacy app never had. | Open |
| D-6 | AWS regions | Phase 8 (config key only in P3-2) | Org-standard pair | **Org-standard pair, e.g. `us-east-1` (Global Database writer) + `us-west-2` (secondary with write forwarding).** The app only reads `LOAN_REGION_ID`. | Phases 3–6 are region-agnostic; region identity is config (`RES-08`, `PLAT-10`). | Open |
| D-7 | Real vs mocked integrations (credit bureau, KYC/watchlist, email) | P6-1 | Integrate real vendors now; keep mocks behind ports | **Keep the current synthetic bureau, static watchlist and log-only email as local adapters behind ports**; real vendors in a later scoped project | Real vendors need contracts, credentials and a data-protection review. Ports plus resilience wrappers make the later swap a config change. | Open |
| D-8 | Business quirks: preserve or fix | P3-4 | Preserve all; fix selected | **Preserve every business quirk in [behavior-parity.md](behavior-parity.md#3-quirk-register)**; fix only the technical defects (TD-*) and the transport-level behavior changes in PRD §6 | Parity is what makes the replatform safe to review; rule changes are business decisions to make separately. | Open |
| D-9 | HTTP mapping of legacy `ERR` outcomes (customer not found, KYC data incomplete, amount ≤ 0) | P5-2 | 200 with `eligibilityCode: "ERR"`; 4xx error envelope | **4xx error envelope**: unknown customer → `422 CUSTOMER_NOT_FOUND`; KYC data incomplete → `422 KYC_DATA_INCOMPLETE`; amount ≤ 0 / invalid term → `400 VALIDATION_FAILED` (checked before business logic, `SEC-02`). The domain still returns `ERR`. | `ARCH-03`/`SEC-02` require invalid input to come back as the envelope. A machine client should not have to parse a business code to detect bad input. | Open |
| D-10 | Silent defaults on bad input (term → 36, unparsable money → 0) | P5-1 (API), phase 2 (legacy) | Preserve; reject | **Reject in the JSON API** (`400 VALIDATION_FAILED`). If phase 2 keeps the defaults on the legacy form path, the JSP path keeps them until P5-5. | Same as D-9; the assessment already names this as decision 5. | Open |
| D-11 | Application identifier | P4-3 | UUID only; UUID plus legacy-style `LA…` reference | **UUID (application-generated) only.** Drop `LA<millis>`/`EL<millis>`. | No durable data exists, so no legacy ids need mapping. Millisecond ids collide (TD-1). | Open |
| D-12 | Customer identifier | P4-1 | Keep `C10001`-style business key; switch to UUID | **Keep the business key** (`VARCHAR(20)`) as the primary key and path parameter | Customers are reference data owned upstream; renumbering would change the API contract for no benefit. | Open |
| D-13 | Data-access technology | P4-2 | Spring JDBC (`JdbcClient`); JPA/Hibernate; jOOQ | **Spring JDBC `JdbcClient`** with hand-written SQL | Closest to the existing parameterized SQL (`SEC-07`), so the port is reviewable line by line. No ORM state or lazy-loading surprises. | Open |
| D-14 | Where seed customers C10001–C10004 exist | P4-1 | All envs; non-prod only; local/test only | **Local, test and integration only** (Flyway location enabled by profile); never prod | They are test fixtures, and C10004 is a watchlist test record. | **Decided by the Phase 4 task:** seed customers ship in `V2__seed_rates_and_customers.sql` (all environments) for now. Revisit before production (C10004 is a watchlist test record). |
| D-15 | Module-boundary tooling | P3-3 | Plain ArchUnit rules; Spring Modulith (ArchUnit-based) | **Plain ArchUnit** | Explicit rules that are easy to review. Spring Modulith can be adopted later if its event-publication registry is wanted instead of the hand-rolled outbox. | Open |
| D-16 | Real email provider | After phase 6 | Not in the approved-platform table | **Defer.** Keep the `EmailSender` port with a redacting log adapter. A provider needs a platform decision or exception. | `PLAT-09`: don't propose a stack element the standards don't list. | Open |
